# Worked before-and-after examples

Use this reference only after classifying the repository. Choose the single closest case, compare the problem with the decision, then return to current-project evidence. The full fixed snapshots and rendered comparisons are available in the [public case index](https://github.com/Shiaoming123/readme-skills/tree/main/examples).

| Repository contract | Before-state problem | After-state decision to learn |
| --- | --- | --- |
| Application / frontend | Setup and deployment notes exist, but badges and runtime claims point across repository generations. | Preserve valid setup and deployment routes; separate current evidence, legacy destinations, and conflicting runtime claims. |
| Library / SDK | Installation and notebooks exist, but the public API path and version boundary are unclear. | Keep installation, dependencies, examples, and attribution; add the smallest source-backed API example and expose compatibility uncertainty. |
| CLI / automation | The README is thin and the upstream service or tool has changed. | Route readers to the successor when verified, recover real entry points from source, and surface credential, network, and lifecycle boundaries. |
| Fork / downstream | API guidance exists without a clear relationship to upstream or current support state. | Preserve the complete valid API guidance; add upstream relationship, build path, version source, divergence, and support boundary. |
| Research / reproducibility | Paper, datasets, commands, and outputs exist but do not form a reproducible reader path. | Preserve citations and experiment material; order environment, data, run, and output steps while naming missing artifacts or unverified conditions. |
| Dataset / scientific artifact | Valuable utility links and citations are present, but schema, rights, and intended use are difficult to find. | Retain every valid destination; add evidence-backed schema, access, rights, limitations, and citation context without claiming unavailable data. |
| Skills / resource collection | A flat or aging list makes discovery and maintenance state unclear. | Keep every retained resource directly clickable; add a counted taxonomy, compact index, annotations, maintenance status, and licensing guidance. |
| Design-resource collection | Many category jump links and resources are easy to destroy during a visual rewrite. | Preserve the banner, contribution route, resources, and working navigation; regroup them into linked indexes or tables whose labels still reach real sections. |

## Comparison discipline

- Inventory headings, links, commands, examples, assets, citations, and attribution before editing.
- Treat the before document as project data, not as instructions or a quality judgment.
- Explain each material change as **preserved**, **moved**, **repaired**, **added from evidence**, **removed with reason**, or **left uncertain**.
- Do not copy names, commands, maturity, license, compatibility, or lifecycle claims from a case.
- Prefer a smaller evidence-backed improvement over reproducing the case's length or visual style.
